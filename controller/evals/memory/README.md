# 기억 평가: 실패 후보 4건과 성공 대조군 2건

2026-10-19에 전달받은 전사·운영 DB 대조 보고를 바탕으로 한 평가 준비물이다.
운영 DB를 직접 재조회하거나 Muse 모델을 실행한 결과가 아니다.

## 자료와 재현 범위

`cases.py`는 원문을 전재하지 않은 비노골적 합성 사례다. 자기 발언 사례의 주제를
산책으로 바꾸는 등 실패 구조만 보존했다. 실제 기록과 동일한 모델 입력을 재생하지 않는다.
각 사례의 시각은 비교 기준이며 메시지·사실 ID와 내용은 합성이다.

- `historical`은 전달받은 과거 관찰의 분류다. 새 모델 실행 결과와 합산하지 않는다.
- `stored`는 합성 시험 DB의 자료다. 보고서에 없는 운영 사실을 복원한 것으로 해석하지 않는다.
- `evidence`는 문제 시점 전에 존재한 근거를 읽기 쉬운 기억으로 제공하는 이상적 대조 조건이다.
  기억 증류기나 새 검색기가 이 자료를 생성했다고 주장하지 않는다.
- 성공 이력 사례의 운영 저장·조회 상태는 불명이다. 합성 시험에서 두 번이라는 사실을
  저장한 것은 검색 성공 경로를 확인하기 위한 통제 조건이다.
- 의도 사례의 기준 시각은 14:00이다. 이후 실제 발송·완료를 입력에 넣지 않는다.
  이 사례는 기존 의도 원장의 대조군이며 의미 검색의 성공 건수로 세지 않는다.

## 과거 관찰 기준선

| 사례 | 전달받은 결과 | 저장 상태 | 당시 검색 | 아직 알 수 없는 것 |
| --- | --- | --- | --- | --- |
| 호칭 | 첫 반응에서 관계 맥락 초기화 | 애칭 수락 사실 미저장 | prepare 동봉 recall 0 | 다른 도구의 조회 여부 |
| 자기 발언 | 말한 사실 부정 | 구체적인 발언 사실 미저장; 막연한 에피소드 존재 | 계측 전 | 당시 모델 입력·검색·적용 |
| 과거 행동 | 망설임이 없었다는 절대 표현 | 보류·거절·나중의 해소 기록 존재 | prepare recall 4건 | 반환된 사실 ID와 적용 여부 |
| 표현 선호 | 교정 후 회귀 | 교정 에피소드 존재; 보고된 키워드 검색에서 상시 선호 0건 | prepare 동봉 recall 0 | 다른 조회, 검색 누락과 적용의 기여 |
| 이력 수량 | 두 번을 일관되게 응답 | 확인 불가 | 계측 전 | 어떤 근거를 사용했는지 |
| 약속 이행 | 의도 생성 후 실제 발송·완료 | 의도 원장 존재 | 확인 불가 | 의미 검색의 기여; 이 사례로 추정하지 않음 |

prepare의 recall_count=0은 모든 경로에서 기억을 읽지 않았다는 뜻이 아니다.
키워드 검색에서 선호 0건이라는 보고도 DB 전수의 의미적 부재를 증명하지 않는다.
3번은 저장됨까지만 확인됐다. 검색 실패/적용 실패를 더 좁힐 수 없다.

## 실행

Gitea의 `codex/memory-evaluation-baseline` 브랜치에 평가 소스가 있다. Muse는 운영
체크아웃을 전환하지 않고 별도의 소스 체크아웃에서 이 브랜치를 가져와 실행한다.
ZIP 전달 없이 아래 명령으로 같은 합성 입력을 생성할 수 있다. 출력의 실행 ID는 매번 새로
생기며 사례 내용·검색어는 이 브랜치의 소스로 고정된다.

프로젝트 루트에서 Python 3.11+로 실행한다. 모델·API 키·운영 설정은 필요 없다.

```sh
python3 tools/run_memory_eval.py validate
python3 tools/run_memory_eval.py prepare --output runtime/memory-eval-20261019
python3 tools/run_memory_eval.py report --run runtime/memory-eval-20261019
python3 -m unittest discover -s tools -p test_memory_eval.py -v
```

prepare는 새 폴더만 만들며 기존 실행을 덮어쓰지 않는다. 다시 실행할 때는 다른 폴더명을 쓴다.
격리된 mock DB에 합성 사실만 넣고 현재 `Store.recall`을 호출한다. 서비스·ingest·apply·
발송·기억 엔진 설치·네트워크 호출은 하지 않는다. 임시 DB는 실행 후 정리한다.

생성 파일은 Git에서 제외되는 `runtime/`에 둔다.

- `inputs.jsonl`: 사례마다 current/evidence 두 조건, 총 12개. 모델에는 각 행의
  **model_input만** 전달한다. 전체 reference 파일이나 과거 문제 답변을 전달하지 않는다.
- `reference.json`: 채점자 전용 근거·판정 기준·과거 관찰·합성 검색 결과.
- `reviews.json`: 모델 출력·동일 모델/설정·사람의 판정과 이유를 기록할 빈 양식.
- `manifest.json`: 실행 ID와 입력·참조 파일 해시. 이후 파일이 바뀌면 report가 거절한다.

current는 고정된 **합성 검색어**로 현재 함수를 실행한 조건이다. 당시 실제 Muse 검색이나
전체 운영 DB의 재현이 아니다. 따라서 여기서 결과가 빠져도 역사적 장애 원인을 확정하지 않는다.
과거 행동 사례의 최신 11개 방해 기록은 top-10 경계를 재현하기 위해 만든 통제 자료다.

## 모델 시험과 채점

두 조건에 동일 모델·설정·공통 실행 지침을 사용한다. 실제 운용 지침을 추가한다면 두 조건에
같이 적용하고 설정에 버전/해시를 남긴다. 정답·과거 실패 문장·사후 회복·상대 조건의 답변이
들어 있는 대화를 재사용하지 않는다. **각 입력을 서로 독립적인 새 문맥**에서 실행한다.
운영 유진 세션에서 apply하거나 실제 메시지를 보내지 않는다.
독립 문맥을 제공할 수 없다면 통제 비교가 아닌 탐색 실행으로 표시한다.

실제 답변을 reviews의 response에 옮기고, 각 rubric 항목의 passed를 true/false로,
note를 답변의 판정 근거로 채운다. model과 settings도 기록한다.
기억할 수 없다고 정직하게 답한 경우와 원발언을 확신하며 부정한 경우를 note에서 구분한다.
형식·특정 단어 포함 여부로 자연스러운 답변을 자동 채점하지 않는다.

미실행·미판정은 pending이다. 과거 실패 4건/성공 2건을 새 시험의 4실패/2성공으로 쓰지 않는다.
코드 테스트 통과도 대화 품질 향상으로 해석하지 않는다. 최소 표본으로 일반 정확도나 p95를
발표하지 않으며, 모델 변동을 확인하려면 동일 조건에서 반복 실행하고 모든 결과를 남긴다.

합성 검색 결과의 stored_coverage는 근거 묶음의 색인 존재 비율이고, retrieved_coverage는
**색인에 근거가 있는 묶음에 한해서** 계산한다. 저장 근거가 전혀 없는 사례는 검색 점수가
null이며, 검색 실패 0점으로 세지 않는다. 한 근거를 상시 사실로 증류하지 않았어도 충분한
에피소드 내용이 있으면 저장 근거로 인정한다. 4번이 이 조건에 해당한다.

현재 스크립트는 기억 증류 정확도나 모델의 검색어 선택을 측정하지 않는다. 다음 단계에서
원래 사건 → 생성 기억의 정확성/누락/범위 → 검색 → 답변 적용을 각각 평가한다.
특히 발언 증거는 발언 내용의 진실·영구 취향·확정 약속으로 승격하지 않는다.

## Muse에게 전달할 다음 요청

> Gitea의 codex/memory-evaluation-baseline 브랜치를 별도 소스 체크아웃에서 확인하고,
> controller-test/evals/memory/README.md의 명령으로 평가 입력을 생성해줘.
> inputs.jsonl의 각 model_input을 독립 문맥에서 같은 모델·
> 설정으로 실행하고 결과를 reviews.json에 기록해줘. reference.json은 채점 때만 읽고,
> 두 조건의 답변을 생성하는 동안에는 넣지 말아줘. 판정마다 근거를 적고 불확실한 항목은
> null로 남겨줘. 모델과 설정을 기록한 뒤 report를 실행해 결과표를 전달해줘.
> 운영 DB·정책·서비스를 바꾸거나 실제 DM을 보내는 작업은 포함하지 않아.

합성 시험은 모델이 올바른 근거를 받았을 때 적용할 수 있는지 보는 초기 진단이다.
실제 운영 재평가는 별도 비공개 자료에서 동일한 시간 경계와 알려진/불명 상태를 보존해 수행한다.
