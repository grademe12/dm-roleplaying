# 생활 운영 원칙과 저장 책임

## 범위와 책임

Muse가 생활 계획과 대화 방향을 판단한다. 문장 작성은 기본 Muse 또는 설정된 선택형 답장 생성기가 맡고, 저장 계층은 시간·중복·상태 일관성을 검사해 결과를 보존한다. 유진의 실제 외부 행동은 설정된 개인 DM이며 공개 피드는 비활성이다. 생활 활동은 시뮬레이션이다. 세션의 생활·관계 상태를 공유하더라도 구조화 기억의 channel/scope 접근 규칙은 [기억 연속성](../runbooks/memory-continuity.md)을 따른다.

이 문서는 생활 판단의 시간·저장 원칙을 담당한다. 실제 입력·검증은 [API](../API.md)와 현행 코드, 실행 순서는 [CRON_RUNBOOK](../CRON_RUNBOOK.md)이 기준이다. 실행 스키마는 상위 `schema/`이며 이 디렉터리의 `schema.sql`은 과거 설계 초안이다. 새 스키마를 기존 운영 DB에 그대로 적용하지 않는다. 현재 소스의 기능과 운영 VM의 배포·활성 상태는 구분한다.

## 시간과 세션

- 한 세션은 하나의 이어지는 캐릭터 세계다. 브라우저 새로고침이나 프로세스 재시작으로 새 세션을 만들지 않는다.
- 저장 시각은 UTC Unix 밀리초 정수다. Muse 입력·출력에는 KST ISO 8601 시각을 표시하고 어댑터가 변환한다. 일자와 주간 계획은 Asia/Seoul 기준이다.
- 실제 현재 시각은 실행 환경에서 공급한다. DM 본문의 날짜를 시스템 시각으로 사용하지 않는다.
- 상태는 `advanced_to_ms`까지 반영되었다고 기록한다. 그보다 이전 시각의 호출은 시간을 되돌리지 않고 새로 도착한 정보만 처리한다.
- 모든 상태 변경은 `revision`을 증가시킨다. Muse가 읽은 revision과 저장 시 revision이 다르면 현재 상태를 다시 읽고 판단한다.

## 저장 상태

| 구분 | 필드 및 의미 |
|---|---|
| 현재 상태 | 장소, 피로·기분·배고픔·사회적 피로 0~100, 마지막 시간 반영 시각, 다음 판단 시각, revision |
| 주간 계획 | KST 월요일 날짜, 재택 날짜 또는 null, 선택 근거, 선택 seed |
| 활동 | 주요 활동 하나, 선택적 동반 활동, 시작·예상 종료·실제 종료, 장소, 집중도, 중단 가능성, 근거 |
| 일정 | 시작·종료, 장소, 확정/제안 여부, 고정 여부, 참여자 |
| DM | 수신 이벤트 ID, 실제 확인한 본문, 관찰 시각, 처리 상태, 답변 예정 시각 |
| 작업 | 실제 DM의 대상·내용, 중복 방지 키, 시도 및 결과 상태 |
| 사건 | 발생 시각과 기록 시각, 출처, 참여자와 내용을 아는 사람, 요약 |
| 대화 소재 | 업무·취미 사건의 흐름 ID, 사건을 사용자에게 실제로 공유했는지, 공유한 시각과 근거 |
| 취미 경험 | 선택한 활동·대상·구체적 결과·유진의 반응·다음 관심, 이미 말한 여부 |
| 관계 목표 | 최초 확인된 1:1 연락의 근거와 KST 날짜, 현재 관계 상태와 그 근거, 목표 재평가 여부 |

미확정 장소·부모 지원액·초기 자산 등은 null 또는 미정으로 유지한다. 상태 수치는 생활 선택을 위한 추상 값이며 건강 측정값이 아니다. 초기값은 예시 기본값을 실제 관측으로 오인하지 않도록 초기화 사건에 기록한다.

실제 수신·발송 확인은 `facts`의 `observed`, 성격과 기본 설정은 `canon`, 역할극 생활에서 선택한 활동·현재 감정은 필요할 때 `simulated`로 구분한다. 지금 떠오른 생각이나 같이 떠들고 싶은 마음도 선제 연락의 이유가 되며, 그때마다 과거 observed 사건을 새로 만들 필요는 없다. 실제 경험을 이야기하면 기존 경험 기록을 확인한다. 현재 관계와 관계 단계는 `relationships.details`와 근거 사건 ID로 보존한다. `relationship-score.md`의 친밀도 점수와 반영한 사건 ID도 같은 `details`에 저장한다. 관계 단계의 변화는 실제 DM에서 그렇게 정리됐다는 근거가 있을 때 기록한다. 무응답만으로 관계 단계나 점수를 바꾸지 않는다. 기존 DB에 새로운 열을 추가할 필요는 없다.

연구실 사건과 취미 경험은 `conversation-world.md`에 따라 현재 활동에서 생성해 `facts`에 보존한다. 이미 말한 소재를 구별할 때는 원 사건을 수정하지 않고 공유 사실을 새 사건으로 기록한다. 사용자의 질문에 응답하면서 처음 언급한 내용만 실제 공유로 처리한다. 이 기록 역시 기존 스키마의 `facts.details`와 별도 사건 ID를 사용한다.

연구실과 주변인은 `bounded-world.md`의 유진 중심 범위로 갱신한다. 연구 흐름과 인물 상태는 `facts.summary`의 안정적인 검색 표식으로 조회하고, 변동이 있을 때만 새 `simulated` 사건으로 기록한다. `tick`은 주변인의 최신 상태를 자동으로 반환하지 않으므로 Muse가 관련 인물·연구에 대해 `recall`을 수행한 뒤 판단한다.

## 활동 전환

`planned → in_progress → completed`를 기본으로 한다. 시작 전 취소는 `cancelled`, 도중 중단은 `interrupted`다. 완료·중단된 활동은 다시 열지 않고 필요하면 이전 ID를 참조하는 새 활동을 만든다.

- 세션당 진행 중인 주요 활동은 최대 하나다. 음악 듣기 같은 동반 활동은 주요 활동 레코드 안에 포함한다.
- 다른 장소의 활동을 시작하기 전에 이동 활동을 둔다. 이동 중 위치는 `in_transit`, 목적지는 별도 필드다. 도착 시 장소를 변경한다.
- 끝 시각을 연장할 때는 다음 확정 일정과 이동 시간을 검사하고 변경 사건을 남긴다.
- 주요 활동의 전체 기간은 서로 겹치지 않는다. 업무를 점심이나 회의로 나누면 각 구간을 별도 활동으로 기록한다.
- 짧은 DM 답변은 활동을 반드시 종료하지 않는다. 집중을 오래 끊는 대화로 바뀌면 중단 또는 휴식으로 기록한다.

## 일정과 활동 선택

확정 일정과 이동 → 식사·수면·필수 생활 → 현재 활동 유지 → 자유시간 활동 순으로 검토한다. 긴급한 사용자 메시지는 즉시 재평가할 수 있지만 일반 DM마다 생활 계획을 재추첨하지 않는다.

재택일은 한 주에 한 번 선택해 저장한다. 첫 실행이 주중이면 이미 지난 날은 재택으로 새로 만들지 않고 남은 근무일에서 고른다. 남은 날에 대면 일정이 모두 있으면 null과 이유를 저장한다. 이후 대면 일정이 추가되면 남은 후보로 명시적으로 변경하거나 해당 주 재택을 취소한다.

기상은 하루 한 번 계획한다. 전날 취침·피로를 보고 평일 10:30~11:30, 주말 12시 이후를 기본으로 결정한다(취침은 새벽 3시 전후). 늦잠은 별도 사건으로 기록하고 당일 연구실 도착 시간을 조정한다. 알 수 없는 공휴일을 임의로 적용하지 않는다.

자유시간은 lifestyle.md 후보 중 다음 조건을 먼저 통과한 활동만 고려한다.

1. 준비·활동·이동을 합쳐 다음 일정 전까지 가능하다.
2. 현재 장소·피로·사회적 피로에 맞는다.
3. 비용이 필요한 경우 알려진 가상 예산 안에 든다. 예산이 미정이면 구체적인 구매 확정을 만들지 않는다.
4. 참여자가 있는 경우 일정이 설정되어 있다. 실제 사용자의 수락을 시뮬레이션하지 않는다.

남은 후보는 선호, 최근 7일 활동의 반복, 휴식 필요, 약속과의 연속성을 고려해 Muse가 선택한다. 선택 결과를 저장하며 같은 이벤트를 다시 처리해도 재선택하지 않는다. 모든 취미를 균등한 횟수로 수행할 필요는 없다.

## 상태 수치의 변화

활동을 시작할 때 해당 활동의 시간당 변화량을 기록한다. 수면·휴식은 피로를 낮추고 집중 업무·운동은 높이는 방향이다. 구체적인 계수는 구현 시 조절할 기본값으로 둔다. 식사 완료처럼 한 번 발생하는 효과는 완료 사건에서만 적용한다.

시간 효과는 `advanced_to_ms` 이후 경과 구간에만 적용하고 0~100으로 제한한다. 중복 실행으로 같은 구간의 피로가 두 번 변하지 않는다. 관계 변화는 시간 효과와 분리하여 실제 대화·세계관 사건을 근거로 기록한다.

## DM 처리

수신 적재는 설정된 poller·Slack listener가 맡는다. Muse는 tick의 미처리 메시지와 prepare가 전달한 해당 채널의 최근 대화를 읽고 판단하며, 원문을 다시 수신한 것처럼 중복 적재하지 않는다. 플랫폼 ID·순서·상태가 불확실하면 기존 수신 복구·검토 계약을 따른다. 문맥 확인과 구조화 검토는 [reply-context](reply-context.md), Slack 연결은 [SETUP](../slack/SETUP.md)을 따른다.

- 편한 휴식 중이면 현재 대화 흐름에 맞춰 답할 수 있다.
- 집중 업무·게임 중이면 가까운 휴식 또는 종료 시점으로 `reply_due`를 정한다.
- 운동·수면 등 `unavailable`이면 초안을 만들지 않고 종료 또는 기상 시점으로 미룬다. 수면 중 Slack 알림만 게이트의 고정된 확률 판단에 따라 수면을 중단하고 답할 수 있다.
- 한 메시지에 대해 정한 답변 시각을 이유 없이 계속 뒤로 미루지 않는다. 변경 시 이유와 새 시각을 기록한다.
- 연속 메시지는 답변 대상을 하나의 묶음으로 정할 수 있다. 새 메시지가 오면 아직 발송하지 않은 초안을 재검토한다.
- 주기적으로 깨웠다는 이유만으로 먼저 연락하지 않는다. 선제 DM은 현재 맥락과 기존 발송 권한 안에서 별도로 판단한다.

실제 발송 상태는 `pending → attempting → submitted → confirmed`다. 발송 전 중단이 확실하면 failed, 발송 여부가 불확실하면 unknown이다. submitted는 입력·제출까지만 확인한 상태이고 confirmed는 전송된 말풍선 등 실제 발송 증거가 있는 상태다. 상대가 읽었다는 뜻은 아니다. submitted/unknown은 확인 없이 재시도하지 않는다.

## 실행 절차와 저장 경계

선점 → prepare → 선택된 실행 경로 → 검토·commit → 발송·후속 처리는 [CRON_RUNBOOK](../CRON_RUNBOOK.md)을 따른다. 이 문서에 별도 실행 순서를 유지하지 않는다. DM 턴에서 처리할 필수 생활 경계는 [life-boundaries](../runbooks/life-boundaries.md), 생활 선택은 [life](../runbooks/life.md)와 [activity-selection](../runbooks/activity-selection.md)을 따른다.

상태·사건·결정 저장은 짧은 트랜잭션으로 처리한다. 모델 판단이나 실제 발송 동안 DB 트랜잭션을 열어 두지 않는다. 발송 작업의 선점·결과 기록·불확실 상태 복구는 컨트롤러와 전송 워커가 담당하며, Muse가 별도 작업 상태 전이 절차를 만들지 않는다.

SQLite와 외부 DM 사이에는 하나의 원자적 트랜잭션을 만들 수 없다. 따라서 이 설계는 중복 위험을 줄이고 불확실한 결과를 보존하며, 외부 전송의 완전한 exactly-once를 보장한다고 주장하지 않는다.

## 다음 실행과 중단 복구

다음 판단 시각은 활동 종료, 확정 일정의 준비 시작, 미룬 DM 답변 시각 중 가장 이른 미래 시각이다. 업무 중에는 휴식 시점도 후보가 된다. 현재 시각 이하의 값을 반복 예약하지 않는다. 새 DM은 예약 시각과 무관하게 별도 이벤트로 처리한다.

장시간 중단 후에는 현재까지의 일상 경과를 큰 구간으로 보충한다. 사용자가 참여한 새 사건·약속 수락·실제 DM 발송을 만들어내지 않는다. 보충 사건에는 실제 발생 시각과 나중에 기록한 시각을 구별한다. 중단이 하루 이상이면 끼니·업무·휴식을 요약하고 과거의 세세한 대화나 작품 감상 내용을 대량 생성하지 않는다.

깨우기 기능이 없으면 `on_input` 모드로 표시한다. 이 경우 다음 DM 또는 수동 실행 때 경과를 반영하며, 예약한 답변이 제시간에 실행된다고 보장하지 않는다.

## 기존 세션 도입

새 생활 DB에 기존 DM 관계·확정 기억을 출처와 함께 가져온다. 원본 DB는 보존한다. 현재 장소와 활동이 불명확하면 unknown으로 초기화한 뒤 현 시각에 맞는 계획을 시작하고, 이미 연구실에 갔거나 식사했다는 과거를 관측 사실로 만들지 않는다. 메신저는 유진 전용 Slack DM 설정을 사용한다.
