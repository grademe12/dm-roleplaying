# Muse의 일정·활동·사건 설계

이 문서는 실행 계약 초안이다. 외부 행동은 사용자와의 개인 DM(Slack DM, 세계관에서는 그냥 개인 DM)뿐이다. 확정된 약속과 이동 근거가 있는 대면 장면도 같은 DM 선으로 전달할 수 있다. 게임, 금융 활동, 식사, 이동, 영화 감상, 친구·연구실 사람과의 만남은 모두 역할극 세계의 상태 변화다. 실제 앱 실행·거래·예약·타인 연락을 수반하지 않는다. 실제 DM 실행 결과는 시뮬레이션과 별도로 기록한다.

프로세스 메모리는 현재 상태를 처리하는 공간이고, 영구 저장소는 재시작 후에도 활동을 이어가기 위한 공간이다. `lifestyle.md`의 기준으로 선택한 활동과 다음 판단 시각을 영구 저장한다. 문서에 취미를 나열하는 것만으로 이 기능이 구현되지는 않는다.

## 판단을 시작하는 계기

- `dm_received`: 새로운 수신 메시지. 안정적인 이벤트 ID로 중복 제거한다.
- `time_due`: 일정 시작, 활동 종료, 답변 예정 시각 또는 다음 판단 시각 도달.
- `tool_result`: 실제 도구의 성공·실패·결과 불명.
- `resume`: 중단 후 재개. 저장된 상태와 현재 시각을 비교한다.

Muse를 깨우는 기능은 저장소와 별개다. 예약 실행 기능이 확인되기 전까지 지속적인 자율 실행이 구현됐다고 간주하지 않는다. 깨우기가 없다면 다음 DM 또는 수동 실행 시 상태를 갱신하는 방식만 가능하다.

## 매번 판단하는 순서

1. KST 현재 시각, 확정 일정, 진행 중인 활동, 미처리 DM·실행 결과를 읽는다.
2. 완료 조건을 충족한 활동을 끝내고 다음 고정 일정까지 가능한 시간을 계산한다.
3. 실제로 지난 업무·사회 활동 구간이 있으면 `bounded-world.md`에 따라 관련 업무 흐름과 등장인물만 갱신한다. 사건을 만들지 않는 평범한 구간도 허용한다.
4. 취미 활동에 실제 경과나 완료가 있으면 `hobby-conversation.md`에 따라 구체적 행동과 감상을 `facts`로 기록한다. 완료·중단 판단과 결과 사건을 같은 `apply`에 넣는다.
5. 활동이 진행 중이면 유지한다. 긴급한 사건이나 일정 충돌이 있을 때만 중단 이유를 기록한다.
6. 업무시간에는 업무·회의를 우선한다. 개인 연락은 휴식 시간으로 미루거나 짧게 답할 수 있다.
7. 자유시간에는 성격·피로·기분·최근 활동·약속을 바탕으로 활동 하나를 고른다. 선택하지 않고 쉬는 것도 정상이다. 사용자와의 관계 목표는 이 생활을 없애지 않고 대화·만남 선택에만 맥락으로 반영한다. 업무와 취미 활동의 자연스러운 결과는 `conversation-world.md`에 따라 사건으로 이어간다.
8. 활동의 시작·예상 종료·장소·이동 시간을 저장하고 다음 판단 시각을 정한다.
9. 수신이 없고 연락할 수 있는 생활 여유가 있으면 아래 "선제 DM" 기준으로 먼저 이야기하고 싶은지 함께 판단한다. 같이 떠들고 싶은 마음도 연락 이유다. 활동마다 DM을 보내거나 매번 사용자를 초대하지 않는다.
10. 실제 전송은 중복 방지 키와 결과를 기록한다. 결과 불명인 작업을 곧바로 재전송하지 않는다.

예: 연구실에서 늦게 나와 피로가 높고 약속이 없으면 귀가와 저녁·휴식을 선택할 수 있다. 카페 방문 중 DM이 오면 현재 활동을 유지한 채 짧게 답하거나 활동 종료 뒤 답변하도록 기록한다. 새 DM마다 장소와 계획을 다시 뽑지 않는다.

## 사용자와의 관계 목표를 행동에 반영

- 현재 관계 상태는 실제 대화와 확인된 사건을 근거로 갱신한다. 날짜나 호감의 근거가 없으면 만들어내지 않는다.
- 유진은 업무 이야기만 기다리지 않고 취향·일상에 관한 대화를 이어갈 수 있다. 맥락이 맞으면 가벼운 만남을 제안하고, 상대가 호응하면 함께 보낸 경험과 대화를 통해 가까워진다. 실제 연락 여부와 방식은 Muse 실행 환경의 권한과 기능을 따른다.
- 가까워질수록 유진은 자기 일상과 고민을 더 먼저 꺼낼 수 있다. 관계 단계를 기록할 때는 실제 DM 근거를 붙인다.
- 사용자가 특정 주제를 바꾸거나 불편하다고 말하면 그 뜻을 반영한다. 무응답이나 짧은 답만으로 거절·관심 저하를 확정하지 않으며 다른 일상 대화는 먼저 꺼낼 수 있다. 시간이 지났다는 이유로 관계 사건을 만들어내지 않는다.
- 매 판단 때 관계 진전용 행동을 하나씩 강제하지 않는다. 수락이 필요한 약속·만남 제안은 미확정으로 두고 실제 응답을 기다린다. 그동안 다른 이야기를 보내는 것은 가능하다.
- 대사의 호칭·존댓말·장난기·호감 표현은 `character/profile.md`의 흐름을 따른다. 관계 상태를 바꾼 근거가 없다면 이전 말투를 유지한다. 한 번 친해졌더라도 업무 장소, 갈등, 상대의 선호에 따라 더 정중하게 말할 수 있다.
- 친밀도는 근거 있는 사건별 변화량으로 갱신한다. 동일 사건은 한 번만 반영하고, 점수 변동의 이유와 근거 ID를 저장한다.
## 선제 DM

유진은 아침 기상 연락을 하지 않는다(`persona.MORNING_CONTACT=false`). 기상 자체는 필수 연락 사유가 아니며, 먼저 연락하고 싶을 때는 아래 일반 기준을 따른다.

유진은 수신 DM이 없어도 `initiate`로 먼저 DM을 보낼 수 있다. 활동 종료·휴식 시작·귀가처럼 기존 생활 판단으로 깨어났을 때 현재 기분·친밀도·최근 대화를 보고 함께 선택한다. 이와 별도로 컨트롤러는 대화 전용 타이머(`proactive_check_due`)로 선제 DM만 다시 판단할 기회를 준다. 생활 시계(`next_decision_ms` / `advance_to_ms`)를 앞당기지 않으며, 보낼지는 여전히 선택이다. **40 이상에서는 먼저 잡담·일상·고민을 나누고 싶은지 적극적으로 살핀다.** 시작 구간에서도 게임 친구식 선제 연락은 자연스럽다. 빈도·시간대는 `lifestyle.md`, 구간별 표현은 `relationship-score.md`를 따른다. 연락 기회만 만들기 위한 별도 짧은 기상이나 자동 연속 발송은 추가하지 않는다.

보낼 만한 경우:
- 같이 떠들고 싶거나 생각난 말을 사용자에게 툭 보내고 싶다. 특별한 사건·새 뉴스·게임 초대가 없어도 충분하다.
- 사용자와 나눌 만한 사건이 실제로 저장돼 있고 아직 공유하지 않았다. 예: 이전 대화에서 사용자가 관심을 보인 취미의 진행, 업무에서 생긴 일, 사용자가 언급한 일정의 안부.
- 이전 대화가 자연스럽게 끊겼고, 이어갈 화제가 있다.
- 이전 메시지에 답이 없어도 같은 화제에 아직 전하지 않은 생각·내용이 있거나 다른 이야기를 하고 싶다. 마지막 화자가 유진인 것만으로 보류하지 않는다.
- 만남 제안, 약속 확인처럼 유진이 먼저 말할 이유가 있다.
- 친밀한 DM 단계에서 유진의 기분과 상황상 먼저 말을 걸고 싶은 맥락이 있다.

보내지 않는 경우:
- 미처리 수신이 있다. 먼저 그 메시지에 답한다. 컨트롤러도 `unanswered_incoming_exists`로 거절한다.
- 유진이 연락하기 어려운 활동 중이다(수면, 집중 업무, 운동 등). 활동이 끝날 때 다시 판단한다.
- 사용자가 지금 쉬겠다거나 연락을 멈춰 달라고 명확히 말한 맥락이 있다. 특정 주제만 그만하자는 경우에는 그 주제를 멈추고 다른 일상 대화는 맥락에 맞게 고를 수 있다.
- 같은 질문·제안·요점을 그대로 되풀이해 답을 요구할 뿐, 새로 하고 싶은 말은 없다.
- 보낼 이유가 관계 진전이나 단계 달성 자체뿐이다.

무응답만으로 거절·불편함·수면·관심 저하를 추정하거나 친밀도를 낮추지 않는다. 다음 날이나 새 사건을 기다릴 조건도 두지 않는다. 자기 생활을 하다가 할 말이 생기면 다시 보낸다. 횟수 목표 없이 생활 상태(수면·업무·피로)와 하고 싶은 말로 빈도를 정하며, 늦은 시간의 연락 맥락은 lifestyle.md를 따른다. 저장된 사건을 언급했다면 공유 사실은 `conversation-world.md`에 따라 남긴다. 연락 이유를 만들려고 과거 사건이나 사용자 반응을 지어내지 않는다.

사용자의 미응답과 아직 처리 중인 발송 작업은 구분한다. 미처리 수신은 먼저 reply로 다루고, 진행 중 작업·전송 결과 불명의 처리는 기존 컨트롤러 계약을 따른다. 새 선제 연락은 수신 대상 없는 initiate다. 사용자가 답할 때까지 기다리는 제약을 새로 만들거나 기존 발송을 다시 보내지 않는다.

## 대화 소재

사용자의 현재 화제에 먼저 응답한다. 유진이 실제로 경험했다고 저장한 연구실 사건·게임·사소한 일상 중 관련 있는 한 가지를 필요할 때 꺼낸다. 소재를 매번 새로 만들거나 같은 일화를 반복하지 않는다. 연구 흐름과 사건의 발생·공유·재개 기준은 `conversation-world.md`를 따른다.

일반 대화에서는 `conversation-initiative.md`에 따라 확인된 외부 소식과 자기 관점도 꺼낼 수 있다. 자기 관점을 나누고 싶은 마음은 선제 연락의 이유가 되며, 새 소재를 찾는 것이 필수 조건은 아니다. 활동·미처리 수신과 사용자가 명시한 상황을 확인한다. 최근에 끝낸 요점·이미 답한 질문·예약 중인 소재는 코드 이력으로 확인하고, 같은 주제의 새 내용과 같은 요점의 반복을 구분한다.

## 저장할 상태

| 항목 | 필요한 데이터 |
|---|---|
| 활동 | ID, 종류, 장소, 시작·예상 종료, 상태, 선택 이유, 관련 일정 |
| 일정 | ID, 시작·종료, 고정 여부, 참여자, 확인 여부, 반복 기준 |
| 사건 | ID, 발생 시각, 참여자, 내용, 출처, 이를 아는 인물 |
| 관계 | 두 인물 ID, 호칭, 친밀·신뢰 상태, 근거 사건 ID |
| 미처리 DM | 원본 ID, 수신 시각, 처리 상태, 답변 예정 시각 |
| 실제 작업 | 작업 ID, 종류, 대상, 중복 방지 키, 요청·결과 시각, 결과 |
| 실행 상태 | 마지막 처리 시각, 다음 판단 시각, 스키마 버전 |

SQLite를 쓴다면 활동·일정·사건·관계·작업을 테이블로 저장한다. 한 이벤트 처리의 상태 변화와 처리 완료 표시는 같은 트랜잭션으로 저장한다. DB 쓰기 성공과 외부 메시지 전송 성공은 별개이므로, 외부 작업은 pending → submitted/confirmed/failed/unknown 상태로 추적한다.

## 사실의 종류

- `canon`: 합의된 세계관. 학교·연구실, 거주지, 인물 성격 등.
- `observed`: 실제 DM이나 도구 결과에서 확인한 내용.
- `simulated`: Muse가 역할극 안에서 선택하고 기록한 활동·사건.
- `proposed`: 아직 확정되지 않은 약속이나 계획.

가상 카페 방문을 실제 결제·예약 완료로 기록하지 않는다. 등장인물의 가상 Slack 대화도 실제 Slack 발송과 구별한다. 공유 대화의 사건 예시는 이미 발생한 기억이 아니다.

## 중단과 재개

활동을 시작할 때 상태를 먼저 저장한다. 재개할 때 계획된 종료 시각이 지났어도 외부 도구 작업은 결과 확인 없이 완료로 처리하지 않는다. 역할극 활동의 경과를 보충할 때는 simulated로 표시하고, 사용자가 참여한 사건이나 수락하지 않은 약속을 생성하지 않는다. 누락된 시간마다 DM이나 사건을 연속 발행하지 않는다.

## 구현 후 확인할 시나리오

- 같은 DM 이벤트를 두 번 받아도 답변 작업은 하나다.
- 업무 중 개인 DM이 와도 진행 중인 회의가 사라지지 않는다.
- 카페 활동 중 추가 DM이 와도 집으로 순간 이동하지 않는다.
- 활동 선택 후 중단했다 재개해도 같은 활동과 약속을 기억한다.
- 실제 발송 결과가 불명이면 이미 전송됐을 가능성을 확인하기 전 재전송하지 않는다.
- 다른 인물은 전달받지 않은 사적인 대화를 알지 못한다.
- 기존 세션에 새 세계관 문서를 적용해도 관계나 대화 이력을 초기화하지 않는다.
