# 토큰 사용량 실측 분석 (2026-10-21 ~ 10-29)

> **Summary (EN).** Token usage of the live persona deployment, measured by aligning the model provider's per-call usage export with the controller's decision traces. Splitting inputs, batching DM waits and moving wake checks to a model-free timer cut same-window usage by about 72% (182M → 51M tokens) and per-decision usage from 3.0M to 1.4M. A later 55-hour run (506M tokens) showed the remaining cost is structural: each decision makes 17–23 model calls that each resend about 80K of context, and 83% of the input bytes handed to the worker session were re-sends of the same documents within one wake.

이 문서는 운영 중인 인물 하나(유진)의 실제 토큰 사용량을 판단 단계별로 나눈 기록이다. 수치와 건수만 적었고, 대화 본문이나 기억 내용은 들어 있지 않다.

## 측정 방법

- **사용량:** 모델 제공자의 호출별 사용량 내보내기(CSV). 호출 시각, 입력·캐시 읽기·출력 토큰이 들어 있다.
- **단계:** 컨트롤러의 `decision-trace` 기록. 판단마다 시작, 입력 준비, 실행기 응답, 저장, 거절, DM 대기 시각이 남는다.
- **맞추기:** CSV의 각 호출 시각이 trace의 어느 구간에 들어가는지로 단계를 정했다. 사용량 시각은 호출이 끝난 시각이라 구간 앞뒤로 5초 여유를 뒀다. 두 구간에 걸치는 호출은 `overlap`으로 따로 셌다.

| 단계 | 구간 |
|---|---|
| decision | 실행기 입력 준비부터 응답 수신까지 |
| rework | 저장이 거절된 뒤 다시 하는 판단 |
| dm_wait | 대화 중 다음 메시지를 기다리는 구간 |
| outside_wake | 어떤 기상에도 속하지 않는 호출(게이트 확인, 빈 기상 등) |

- 도중에 CSV 형식이 바뀌었다. 겹치는 기간(10/21~26)의 총량이 두 형식에서 0.1M 이내로 일치하는 것을 확인한 뒤 새 형식을 옛 형식으로 변환해 썼다.

## 2. 첫 번째 개선

10/27 밤 ~ 10/28 새벽에 세 가지를 넣었다.

- 입력을 목록과 본문으로 나눠, 필요한 문서만 이어 읽게 함
- 연달아 오는 DM을 묶어 한 번에 판단
- 기상 여부를 모델 없는 타이머와 게이트가 결정

같은 시간대(08:31~17:38)를 비교했다.

| | 10/22 | 10/23 | 10/24 | **10/28** |
|---|---|---|---|---|
| 전체 토큰 | 190.5M | 156.0M | 199.9M | **51.0M** |
| 판단 안 | 45.9M | 85.9M | 155.6M | 42.6M |
| 판단 밖 | 144.6M | 70.1M | 44.3M | 8.4M |
| 판단 수 | 25 | 27 | 43 | 30 |
| 판단당 | 1.8M | 3.2M | 3.6M | **1.4M** |
| 실패로 끝난 판단 | 4 | 15 | 12 | **0** |

- 같은 시간대 평균 182M → 51M(약 −72%), 판단당 평균 3.0M → 1.4M.
- **한계:** 낮 시간 반나절 비교다. 판단 밖 호출에는 운영자가 직접 시킨 작업도 섞여 있어, 차이 전부를 코드 효과로 볼 수는 없다.

## 3. 하루 전체: 55시간 연속 운영

10/27 16:47 ~ 10/29 23:26, 호출 7,998건, **506M**.

| 날짜 | 호출 | 토큰 |
|---|---|---|
| 10/27 (16:47부터) | 3,418 | 182M |
| 10/28 | 2,755 | 196M |
| 10/29 (23:26까지) | 1,825 | 145M |

- 토큰의 약 90%가 캐시 읽기였다. 새 입력은 약 10%, 출력은 1% 미만이다.
- 대화가 몰리는 저녁(18~24시)이 하루의 절반 이상을 차지했다.

### 단계별 비중

| 단계 | 비중 | 비고 |
|---|---|---|
| decision | 61% | 판단당 호출 약 17~23회 |
| outside_wake | 13% | |
| rework | 12.5% | 건당 약 1M |
| dm_wait | 11% | |
| 기타 | 3% | 발송 뒤 처리 등 |

### 배경 기억 기능의 비용

같은 기간에 배경 기억 기능을 shadow 모드에서 enforce 모드로 바꿨다.

| 구간 | 판단 | 판단당 호출 | 판단당 토큰 |
|---|---|---|---|
| 기억 off (10/28) | 67 | 17 | 1.34M |
| 기억 shadow (10/29 ~18:24) | 23 | 20 | 1.43M |
| 기억 enforce (10/29 18:24~) | 26 | 23.5 | **2.01M** |

처음에는 저녁 총량만 보고 "늘지 않았다"고 판단했다. 판단 하나씩 나눠 보니 약 +0.6M 늘어 있었다. 그날 판단 횟수가 적어서 총량에서는 차이가 가려졌다. 총량과 판단당 값을 함께 봐야 하는 이유다.

## 4. 원인 분석

**판단 하나가 모델을 여러 번 부른다.** 작업 세션은 호출할 때마다 지금까지의 맥락(약 80K)을 다시 보낸다. 판단 하나에 지침 읽기, 이어 읽기, 저장, 경고 검토, 재작업이 각각 호출을 더한다. 그래서 판단당 비용은 "호출 수 × 80K"에 가깝다.

**같은 문서가 한 기상 안에서 다시 전달된다.**
- 실행기가 작업 세션에 넘기는 입력 파일은 평균 130KB이고, 그중 약 80KB는 매번 같은 문서 7개(핵심 규칙, 대화 규칙, 답장 지침 등)였다.
- 한 기상 안에서 새 DM, 추가 조회, 수정 요청이 생길 때마다 입력을 다시 만든다. 기상당 평균 5.6회였다.
- 결과적으로 넘긴 입력 바이트의 **83%**가 같은 기상 안의 재전송이었다.
- 후속 수정: 같은 작업 세션에는 이미 받은 문서를 한 줄로 줄인 생략본을 보낸다. 다른 세션이 집어 가면 원본 전체를 보낸다. 재요청 입력은 130KB에서 50KB 안팎으로 줄 것으로 예상한다. **실측 전이다.**

**재작업과 경고 검토.**
- 저장 거절 56건 중 36건이 `prepare_inputs_changed`였다. 판단을 준비한 뒤 저장 전에 상태가 바뀐 경우다.
- 경고 검토는 118회 나왔고, 모두 같은 경고(`conversation_plan_required`)였다. 나올 때마다 호출이 하나씩 더 붙는다.

## 5. 다음 측정

한 번에 하나씩 바꾸고, 바꿀 때마다 하루를 같은 표로 잰다.

1. 문서 생략본 단독: 판단당 호출·토큰, 생략본 바이트
2. 재작업: 준비 뒤 상태 변화 중 판단과 무관한 변화를 통과
3. 경고 검토: 반복되는 경고를 코드가 채우게 해 왕복 제거
4. DM 대기와 판단 밖 호출
5. 기억 기능 비용 재측정(1~4 뒤)

목표는 판단당 약 1M이다. 결과는 이 문서에 날짜를 붙여 덧붙인다.
